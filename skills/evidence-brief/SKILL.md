# Evidence brief

Turn scattered evidence into the document the reader needs to decide or act. Works alone, with connected sources or supplied files. Use an available document-format skill when producing a particular file type; do not add a format or tool requirement to an ordinary chat draft.

## Ground the content

Infer audience, purpose, destination, and expected depth from the request and nearby examples. Read the existing document and any user-supplied style reference. For a proposal, identify the decision. For a weekly update, identify the reporting period and previous update. For meeting follow-ups, distinguish decisions, commitments, suggestions, and unresolved questions.

Read the actual source messages/documents, not only search snippets or chat titles. Search within the authorized topic and period. Follow links needed to understand a claim. Keep a compact private evidence map for substantial work: claim, source/date, what it establishes, and uncertainty. Recheck live status when the output depends on what is true now. Historical chat claims establish what was reported then, not current completion.

Reconcile duplicate accounts of the same work. Show source conflicts rather than quietly picking the convenient one. A count needs a definition, population, time window, and denominator when reporting a rate. Distinguish zero, not checked, inaccessible, and not applicable. Do not infer success or causation from activity alone.

## Write for the reader

Lead with the outcome, proposal, or recommendation. State why it matters in concrete terms. Use the reader's vocabulary and assume the knowledge the audience already has. Match the owner's demonstrated style when available; never transplant another person's voice or private examples into a reusable skill.

Keep only the detail that changes understanding or action. Prefer one bullet per workstream in status updates, with the outcome and material remaining gap. Do not present drafting or investigation as shipped work. Put detailed methodology in linked supporting material when it would crowd the brief.

For proposals, state the problem, proposed change, scope, how to judge whether it helped, and genuinely open decisions. Qualitative success can be checked against representative good, bad, and ambiguous cases; it need not become an arbitrary numerical target.

For meeting follow-ups, reuse existing tasks and link the source discussion. Keep tentative ideas tentative. Do not assign people, set deadlines, or create tracking records unless requested or already authorized. A draft action list can leave these unset.

Use a table for comparisons, criteria, or status distinctions. Use a small process diagram when handoffs are otherwise hard to follow. Every depicted relationship needs evidence or an explicit uncertainty label. Avoid implementation detail that does not help this audience.

## Review and deliver

Read as someone seeing the document for the first time. Can they identify the proposal, the evidence, the next decision, and what is still unknown? Challenge the weakest consequential claim. Cut repeated explanations without removing necessary qualifications.

When editing, reread the latest version before writing and preserve human changes. Apply targeted changes instead of replacing the entire document from an old draft. Verify saved content and links if publication was requested. A draft stays a draft; writing it does not authorize sending it. Report the artifact's actual state and any unresolved limitation.

For consequential factual claims and completion reports, use `verify-sources` when installed. Check that each source supports the claim at the strength stated; keep assumptions labeled in saved notes as well as the final artifact.
