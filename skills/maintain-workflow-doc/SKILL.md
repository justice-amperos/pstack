# Maintain workflow doc

Maintain a usable source of truth for the people doing the work. Works with the document tools available in the session; it does not require code or a particular vendor.

## Find the current workflow

Read the target document, relevant examples, and linked procedures or trackers. Determine where instructions belong, where work status belongs, and which surfaces should link to them. Distinguish current behavior from the proposed process. Do not invent a policy, owner, review state, or historical date to fill a blank.

Scope the change to the requested workflow. Resolve material contradictions through evidence or a focused question. Tool access does not authorize changing unrelated pages or records. Prepare a local draft when shared editing is not authorized.

## Make it usable

Adapt an existing accepted template before designing a new one. Put structured information in native properties when the destination supports them: dates, status, people, and links should be sortable or filterable when that helps the workflow. Keep narrative explanation in the body. Use dynamic dates for reusable templates only after verifying how the destination evaluates them.

Choose one canonical document for each responsibility. Link other systems to it instead of maintaining duplicate reports or action lists. Reuse existing tickets. Creating a tracker entry, assigning an owner, changing a status, and sending a notification are distinct actions governed by the request.

Write instructions in the order a person performs them, including how they enter the workflow, what they need, where the result goes, and how they know the step succeeded. Keep exceptions and unresolved decisions visible. Include a compact diagram only when it explains a real handoff more clearly than prose.

Before updating, reread the destination and reconcile any changes since the initial read. Preserve user edits, URLs, attachments, comments, metadata, and out-of-scope content. Prefer targeted edits. If a tool can only replace a whole page and preservation cannot be established, prepare the change without overwriting it.

## Verify the result

Read back saved content, linked destinations, and native properties. For a template or button, exercise the actual creation flow in an authorized sandbox or with an authorized disposable record, then clean up only task-owned test artifacts within permission. Verify dates and defaults on the created record, not merely in the editor. Do not trigger live notifications or create live operational records just to prove a template works without authorization.

Inspect rendered documents or diagrams for readable tables, clipping, broken links, and misplaced content when rendering is available. Use the relevant format skill for files. A tool success response alone does not establish that a document is usable.

Return the canonical link or file, what changed, how it was checked, and any remaining gap. Distinguish a saved template from a tested workflow. If access or tooling prevents verification, name the exact check still needed. Keep a short maintenance note when future changes depend on a source, policy, or unresolved decision.

For consequential factual claims and completion reports, use `verify-sources` when installed. Check that each source supports the claim at the strength stated; keep assumptions labeled in saved notes as well as the final artifact.
